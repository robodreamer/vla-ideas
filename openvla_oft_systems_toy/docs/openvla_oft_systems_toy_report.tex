\begin{abstract}
This note documents a deterministic two-dimensional systems toy informed by OpenVLA-OFT. OpenVLA-OFT changes a VLA action interface by predicting continuous action chunks in parallel and training them with L1 regression. The local question is narrower: with delayed observations and disturbances, how do serial one-action availability, an eight-action parallel chunk, and two chunk-refresh schedules affect tracking? On 96 seeded trials, refreshing after four actions has the highest terminal-window success (33.3\%), whereas refresh-2 has the lowest mean tracking error (0.311) but not the best terminal result. This is an explanatory control result, not an OpenVLA-OFT reproduction or a measurement of its inference hardware.
\end{abstract}

\section{Motivation}

The action interface is a deployment decision, not merely a last-layer detail. A token-by-token VLA head exposes one action only after the next decoding step; when an actuator needs a command before that step completes, the system either waits, holds the previous command, or relies on a separate low-level fallback. A parallel head instead exposes a short sequence at once. That can keep a fast execution loop supplied while the next observation and inference request are in flight, but the suffix was conditioned on an older observation and can become wrong after unmodeled motion or delay.

OpenVLA-OFT is a useful source of this distinction. Its optimized fine-tuning recipe combines parallel action decoding, chunked continuous-action prediction, and an L1 regression target \cite{oftpaper,oftsite,oftcode}. Together these choices replace discrete autoregressive output with a direct continuous control object: a deployment can decode a horizon in one pass, execute its prefix at control rate, and choose when to discard the remainder for a newer prediction. L1 is relevant because the head is trained to regress continuous action coordinates rather than select action tokens; parallel decoding is relevant because those coordinates are concurrently available. Neither property alone determines closed-loop quality: a longer available chunk trades decoder availability against a longer stale-feedback suffix.

This toy isolates that scheduling trade-off with the same analytical controller in every condition. It deliberately does \emph{not} attribute its numbers to L1 training, OpenVLA weights, or a published robot benchmark.

\section{Toy Setup}

The script \texttt{run\_openvla\_oft\_systems\_toy.py} simulates a point state \(p_t\in\mathbb{R}^2\) and velocity \(v_t\) for 7.2~s at \(\Delta t=0.04\)~s (180 plant ticks). A bounded moving target \(g_t\) is formed from sinusoidal coordinates. The controller sees \((p,v)\) delayed by 0.16~s (four ticks), and asks for the clipped continuous velocity
\[
u_t=\operatorname{clip}\!\left(2.4(g_t-p_t)-0.48v_t,[-1.15,1.15]^2\right).
\]
The plant, which is intentionally not the rollout model used to make a chunk, evolves as
\[
v_{t+1}=0.77v_t+0.23u_t+w_t,\qquad p_{t+1}=p_t+\Delta t\,v_{t+1}.
\]
Every ninth tick, including tick zero, \(w_t\) is a seeded Gaussian velocity gust with per-axis standard deviation 0.045; otherwise it is zero. Each trial's target phase, initial position perturbation, and gusts are seeded.

A parallel request rolls the controller forward from the delayed state using a separate imagined update \(v\leftarrow0.78v+0.22u\), \(p\leftarrow p+\Delta t v\), producing eight planned actions. The mismatch between this imagined rollout and the plant, together with delayed feedback and gusts, makes an unexecuted suffix stale.

The comparators differ only in output timing and how much of that planned object they execute:
\begin{enumerate}[leftmargin=1.5em]
  \item \textbf{Serial autoregressive-like:} request one continuous action at a time. A 55~ms configured decode period sets \texttt{busy\_until}; on the 40~ms grid the previous command is held until it is free, so the measured output rate is 12.5 actions/s.
  \item \textbf{Parallel open loop:} make an eight-action continuous chunk and execute all eight actions before requesting another.
  \item \textbf{Parallel refresh-4:} replace the chunk after its first four executed actions, discarding four suffix actions.
  \item \textbf{Parallel refresh-2:} replace the chunk after two actions, discarding six suffix actions.
\end{enumerate}

The parallel rows record a 60~ms \emph{configured interface-latency annotation}, but the script does not advance a parallel \texttt{busy\_until} clock or delay chunk use by it. Thus it is not an end-to-end latency simulator and the 55-versus-60~ms values are not a fair latency race. Parallel chunks are made available immediately on their refresh tick; the experiment tests stale-prefix scheduling and serial holding semantics.

\section{Metrics}

For each method, all metrics are first computed per rollout and then averaged across 96 trials:
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{configured decision latency (ms):} 55~ms for the serial busy period and a recorded 60~ms interface annotation for parallel rows. It is not wall-clock profiling, and only the serial value gates execution.
  \item \textbf{action-output throughput (actions/s):} the number of action values generated divided by 7.2 simulated seconds. It counts all eight values whenever a parallel chunk is generated, including a suffix discarded by refresh-4 or refresh-2. It is therefore output work/availability, not useful executed actions and not the fixed 25~Hz plant rate.
  \item \textbf{mean tracking error:} \(\frac{1}{180}\sum_t\lVert p_t-g_t\rVert_2\).
  \item \textbf{final tracking error:} \(\lVert p_{179}-g_{179}\rVert_2\).
  \item \textbf{terminal-window success:} one if the mean error over the last 20 ticks (0.8~s) is below 0.16, zero otherwise; the table reports its trial mean.
  \item \textbf{jerk proxy:} the rollout mean of \(\lVert\Delta^2u_t/\Delta t^2\rVert_2\). It describes command variation only, not an actuator constraint.
\end{itemize}

\section{Connection to Other \texttt{vla-ideas} Experiments}

This toy occupies the output-interface and refresh-scheduling part of a broader chunked-control design space:
\begin{itemize}[leftmargin=1.5em]
  \item \textbf{Async chunking:} \texttt{async\_chunking\_compare} asks when a next chunk should be planned under inference delay. Here, the open-loop/refresh-4/refresh-2 comparison makes the consequence of consuming or replacing a stale suffix explicit. An async system could use a latency-compensated state estimate rather than this toy's four-tick-old observation when refreshing.
  \item \textbf{TurboVLA direct control:} \texttt{turbo\_vla\_direct\_control} examines the benefit of frequent action-chunk refresh for a direct V+L-to-action policy. This experiment strips away learned visual/language grounding to focus on a related OpenVLA-OFT output head: parallel continuous chunks need an execution policy even after decoding is made fast.
  \item \textbf{B-spline action parameterization:} \texttt{bspline\_action\_parameterization} changes how a chunk is represented and measures smoothness. The OFT toy holds a dense eight-action representation fixed and changes when it is replaced; a practical stack could pair a continuous compact chunk representation with an explicit refresh rule.
  \item \textbf{Path-consistent safety filtering:} \texttt{path\_consistent\_safety\_filtering} keeps proposed geometry while changing timing for safety. Early refresh here changes the proposed suffix instead. The distinction matters: a deployment may need a safety time-law to govern execution between parallel-head refreshes.
\end{itemize}

\section{Interpretation}

All four rows reveal a different part of the interface trade-off. The serial-like condition produces only 12.5 actions/s because its synthetic decoder holds the prior command across its 55~ms busy interval; it has the largest mean error (0.334) and largest jerk proxy (32.89). Parallel open loop doubles generated availability to 25.6 actions/s and substantially lowers jerk (15.23), but executing all eight actions leaves the most stale suffix exposure and the lowest success alongside refresh-2 (28.1\%).

Refresh-4 is the best terminal compromise in this specific sweep: it halves the open-loop execution length, reaches 33.3\% terminal-window success, and improves mean error to 0.316. Refresh-2 further reduces average stale-suffix duration, which explains its best mean tracking error (0.311), but it does not win the terminal metric: it re-anchors every two ticks to a four-tick-old observation, produces twice as many chunk outputs as refresh-4 (100.0 versus 50.0 actions/s under this accounting), and adds more command boundaries. Its final error (0.249) and jerk (19.99) are also slightly worse than refresh-4 (0.245 and 18.96). The result is not that four is an optimal universal refresh period; it is that average error, final-window occupancy, and output work can prefer different schedules when feedback is delayed.

\section{Limitations and Follow-ups}

This is not a faithful OpenVLA-OFT implementation: it has no OpenVLA backbone, images, language, LoRA, learned action head, L1 optimization, LIBERO/ALOHA data, robot kinematics, contacts, or real inference service. Its controller and parallel rollout are analytical, its target is known to the controller except for the imposed state delay, and the output-rate metric deliberately counts discarded parallel suffixes. The asymmetric timing implementation is especially important: serial 55~ms changes control holding, while parallel 60~ms is only recorded metadata. The table cannot support a claim that a parallel VLA beats an autoregressive VLA at a specified real latency.

Useful follow-ups are concrete rather than cosmetic:
\begin{enumerate}[leftmargin=1.5em]
  \item implement an event-driven scheduler that applies sampled inference latency and queueing to \emph{both} interfaces, then report command age, deadline misses, useful executed actions, and discarded action work separately;
  \item export paired per-trial outcomes and sweep observation delay, chunk horizon, gust magnitude, and refresh cadence with uncertainty intervals, so the apparent refresh-4/refresh-2 crossover can be located rather than treated as a point estimate;
  \item predict from a latency-compensated state estimate and compare it with naive delayed-state refresh, isolating whether refresh frequency or state-age compensation drives terminal performance;
  \item replace the point mass with a constrained arm task, a learned continuous chunk head, randomized observations/instructions, and a capacity-matched serial head; combine chunk refreshing with a path-consistent execution/safety layer.
\end{enumerate}
